This leaf module is purely configuration-driven — it wires together three toolchains around the activation Worker whose source lives under `src/activation/`:
- `drizzle-activation.config.ts` declares a Drizzle Kit project using the `d1-http` driver against SQLite, pointing at `src/activation/schema.ts` and emitting migrations into `./drizzle-activation`. The generated SQL files (`0000_activation_init.sql`) plus `meta/_journal.json` form the migration history.
- `wrangler.activation.jsonc` and `wrangler.activation.staging.jsonc` define two separate Workers (`trackdub-activation`, `trackdub-activation-staging`) sharing the same `main` entry (`src/activation/index.ts`) but with distinct D1 databases, custom domains (`activate.trackdub.com` vs `activate.trackdub.dev`), and signing key IDs so production and staging cannot cross-trust.
- `vitest.activation.config.ts` boots the `@cloudflare/vitest-pool-workers` pool, reads D1 migrations from `drizzle-activation`, and injects bindings (including a test signing keypair from `test/activation/test-keys.ts`) so tests execute inside the real `workerd` runtime.
Dependency direction is one-way: these config files reference `src/activation/` and `test/activation/` but nothing in those sources references back to this module. The `drizzle-activation/` directory is an artifact of code generation, not hand-written source.
